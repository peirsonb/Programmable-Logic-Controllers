    \begin{itemize}

\begin{frame}
    \frametitle{Micro-Level vs. Macro-Level}

    \begin{itemize}
        \item High-quality industrial code requires mastery at both the instruction level and architectural level
        \item[Micro (Rung Mechanics)] How individual instructions, logic gates, and execution operate within a single scan cycle
        \item[Macro (Program Layout)] How routines, modules, are organized across the entire controller
        \item Flawless micro-logic fails inside a disorganized architecture; brilliant macro-architecture is useless if individual rungs are buggy
    \end{itemize}
\end{frame}

\begin{frame}
    \frametitle{Micro-Level (Rung Mechanics)}

    \begin{description}
        \item[Boolean Logic \& Flow] Optimizing examine if closed (\texttt{XIC}), examine if open (\texttt{XIO}), and utput coils (\texttt{OTE}, \texttt{OTL}, \texttt{OTU})
        \item[Scan Cycle Dynamics] Understand top Understanding top-to-bottom, left-to-right rung evaluation and memory image updates
        \item[Edge Detection \& Timing] Proper use of One-Shots (ONS/OSR) and timers (TON/TOF) to prevent race conditions
    \end{description}
\end{frame}

\begin{frame}
    \frametitle{Micro-Level Best Practices}

    \begin{itemize}
        \item Keep rungs readable; avoid excessively nested logic
        \item Limit multiple outputs driven by identical conditions across different rungs (destructive double-coils)
    \end{itemize}
\end{frame}

\begin{frame}
    \frametitle{Macro-Level (Program Layout)}

    \begin{description}
        \item[Modular Organization] Dividing code into Tasks (Periodic vs. Continuous), Programs, and Subroutines/Routines
        \item[State Machine Frameworks] Structuring sequences (e.g., PackML, ISA-88, or custom Step/State logic)
        \item[Data Structuring] Utilizing User-Defined Data Types (UDTs) and arrays over unorganized tags
    \end{description}
\end{frame}

\begin{frame}
    \frametitle{Macro-Level Best Practices}

    \begin{itemize}
        \item Enforce a standardized folder/routine hierarchy (e.g., \texttt{00\_Inputs}, \texttt{10\_Modes}, \texttt{20\_Sequence}, \texttt{90\_Outputs})
        \item Decouple hardware I/O mapping from core process control logic
    \end{itemize}
\end{frame}

\section{Micro-Level Programming}

\begin{frame}
    \frametitle{Micro-Level Programming Rules}

    \begin{itemize}
        \item Micro-level (rung level) programming is governed by a series of fixed rules
        \item Some of the rules are based on the idea that ladder logic is based on electrical schematics
        \item Some software (Logix Designer) will allow breaking the rules--it's up to the \emph{programmer} to follow them
    \end{itemize}
\end{frame}

\begin{frame}
    \frametitle{Rule 1 - Rung Construction}

    \begin{columns}
        \begin{column}{0.48\linewidth}
            \begin{itemize}
                \item Each program line is a \emph{rung}
                \item \emph{Condition} instructions go to the left
                \item \emph{Control} instructions go to the right
                \item Each rung must contain \emph{at least} one control
                \item Most rungs contain condition \emph{and} control
            \end{itemize}
        \end{column}
        \begin{column}{0.48\linewidth}

    \frametitle{Rule 2 - One Control per Branch}

    \begin{columns}
        \begin{column}{0.48\linewidth}
            \begin{itemize}
                \item Each branch (level) of a rung can only have \emph{one} control instruction
                \item Control instructions can be placed in parallel but \emph{never} series

\subsection{I/O Mapping}
% Physical I/O mapping routines vs. direct aliasing (buffer layer advantages)

\begin{frame}
    \frametitle{Direct I/O Aliasing}

    \begin{columns}
        \begin{column}{0.48\linewidth}
            \begin{itemize}
                \item Direct aliasing asigns a physical I/O point to an intnernal tag
                \item This is \emph{not recommended}
                \item I/O are \emph{physical devices}--physical devices occasionally break
                \item The system must be taken offline to change the alias and move the tag to another I/O point
            \end{itemize}
        \end{column}
        \begin{column}{0.48\linewidth}
            \begin{figure}
                \centering
                \resizebox{\linewidth}{!}{

            \end{figure}
        \end{column}
    \end{columns}
\end{frame}

\begin{frame}
    \frametitle{I/O Mapping}

    \begin{itemize}
        \item \emph{Mapping} is the preferred method of assigning I/O points to tags
        \item Two subroutines are created--one for input mapping, one for output mapping
        \item One I/O point per rung
        \item A simple \texttt{XIO} and \texttt{OTE} combination is used to assign the I/O to the tag
    \end{itemize}
\end{frame}

\subsection{Input Processing}

\begin{frame}
    \frametitle{Input Debouncing}

    \begin{itemize}
        \item Mapping also allows something aliasing does not--\emph{debouncing}
        \item Debouncing allows us to intentionally delay the time between a physical input turning on and the tag it's tied to turning on
        \item Not required for \emph{all} input points
        \item Good for filtering out ``nuissance'' trips caused by noise
        \item Good for any input that has a tendency to ``blink''--allows us to be \emph{sure} it's on before we use it
    \end{itemize}
\end{frame}

\begin{frame}
    \frametitle{Analog Scaling}

    \begin{itemize}
        \item Analog inputs come is as integers--whole numbers that represent a voltage or current value from the sensor
        \item Most analog cards are 12-bit--the value received by the PLC will be 0-4096
        \item You \emph{can} use this value, but it doesn't mean much to anyone else looking at the code
        \item It is \emph{much} better to scale it to engineering units \emph{before} using it in logic
    \end{itemize}
\end{frame}

\begin{frame}
    \frametitle{Allen-Bradley Scaling}

    \begin{itemize}
        \item Allen-Bradley's preferred method in the Logix 5000 PLCs is to scale the value in the definition of the analog card itself
        \item This works, but has serious drawbacks
        \item Not all cards and input devices are equal--if you swap temperature sensors and it's off compared to the old one the scaling needs to be changed
        \item If the scaling is in the card definition, the system needs to be taken offline to change it
        \item Plus, not all manufacturers do it this way--we like ``hardware agnostic'' programming methods
    \end{itemize}
\end{frame}

\begin{frame}
    \frametitle{Setting the Scale (1 of 2)}
    \begin{itemize}
        \item Math would tell us the scaling factor would be: $\text{Engineering Units} = \texttt{UnitRange} \times \frac{\texttt{AnalogValue}}{\texttt{MaxValue}}$
        \item But this is only ever going to get you close--not all sensors and cards are equal
        \item Best practice is to actually \emph{measure} the conversion factor
        \item In this case, a spreadsheet is your best friend\dots
    \end{itemize}
\end{frame}

\subsection{Output Management}

\begin{frame}
    \frametitle{Outputs Subroutine}

    \begin{itemize}
        \item Where input grouping is used for readability of the logic, output grouping is \emph{necessary} for machine safety
        \item An \texttt{Outputs} subroutine is used to create the \emph{permissives} for machine motion--those conditions that are required to make sure the machine doesn't crash into itself
    \end{itemize}
\end{frame}

\begin{frame}
    \frametitle{Output Seal-In}

    \begin{itemize}
        \item Output latching instructions and retentive outputs can be dangerous--they're still energized when the PLC power cycles
        \item A \emph{seal-in} is the preferred method
        \item A seal-in uses only an \texttt{OTE} instruction, guaranteeing that the output will turn off on a power cycle
    \end{itemize}
\end{frame}

\begin{frame}

    \begin{itemize}
        \item The techniques discussed up to this point are intended primarily to make it easier for technicians and engineers to troubleshoot the code

\begin{frame}
    \frametitle{Logic Documentation}

    \begin{itemize}
        \item All PLC platforms inlcude a way to \emph{document} the code--usually called \emph{commenting}
        \item Most platforms allow for rung comments \emph{and} tag comments (descriptions)
        \item \textbf{USE THEM BOTH!}
        \item The benefits are two-fold: a technician troubleshooting at 2am will have an easier time understanding what the program is doing, and in 5 years \emph{you} will remember what you did!
    \end{itemize}
\end{frame}
